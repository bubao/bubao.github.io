依赖治理：lock 文件、版本锁定与自动化更新

前几篇讲的是运行时、工具链与检查卡口，还有一个维度容易被低估：依赖。同一份代码，今天装依赖和明天装依赖，结果可能不同；换台机器、换个时间，构建产物就可能变了。

AI 编码助手会进一步放大这个风险：它写代码快，也常常顺手引入新依赖——如果没有锁定与评审机制，AI 可能把未审核的包、错版本的包带进项目。

本文讲依赖治理：lock 文件为什么存在、版本要锁到多严、以及怎么让「升级」变成可控的常规动作。本文承接检查左移，下一篇是命令收口。完整导航见文末。

一、依赖治理解决什么：从「能跑」到「可复现」

依赖声明（package.json 里的 "react": "^19.0.0"、go.mod 里的 require、vcpkg.json 里的依赖）表达的是意图与范围，不是事实。真正装到哪个版本，取决于「解析的那一刻」：

  • 注册表里 ^19.0.0 今天可能解析到 19.0.1，下个月可能解析到 19.2.0；
  • 传递依赖（依赖的依赖）同样会漂移，而且你未必知道它们的存在；
  • 不同人、不同时间、不同 CI 节点，装出来的树可能不完全一样。

结果就是那句经典的「在我机器上是好的」。 SemVer（语义化版本）本意是用 MAJOR.MINOR.PATCH 传达兼容性意图（见 Semantic Versioning），但它是发布者的承诺，不是安装时的保证——所以需要 lock 文件把「事实」固定下来。

对 AI 来说，这一点尤其重要：AI 在生成代码、跑命令、装依赖时，默认会按解析时刻的最新结果来。没有 lock，它装到的可能根本不是项目正在用的版本；有了 lock，AI 的操作与团队基线一致。

二、三层锁定：声明、lock、锚点

依赖版本管理可以分成三层，强度递增：

层次例子表达什么强度
声明package.json 的 "react": "^19.0.0"、go.mod 的 require、vcpkg.json意图 / 兼容范围弱（随时间漂移）
Lockpackage-lock.json、pnpm-lock.yaml、yarn.lock、go.sum、Cargo.lock、conan.lock精确版本 + 完整性校验强（可复现）
锚点vcpkg 的 builtin-baseline、git 依赖的 commit rev、包 digest、vendor/ 目录不可变引用最强（抗篡改）

Lock 层是主力。 以 npm 为例，package-lock.json 官方文档写明：它「describes the exact tree that was generated, such that subsequent installs are able to generate identical trees, regardless of intermediate dependency updates」——也就是把解析结果固定下来，让后续安装得到同一棵树，并带有 integrity（sha512/sha1）校验。pnpm 的 lockfile 里也能清楚看到 specifier（你声明的范围）与 version（实际解析到的精确版本）的区分。

锚点层用于更高要求的场景。 例如 vcpkg 用 builtin-baseline 锁定整个 registry 到某个提交；Cargo 文档里那个例子很直观：git 依赖如果不写 rev，今天构建和明天构建可能取到不同 commit，而 Cargo.lock 会把用到的精确 SHA 记下来，保证可复现。

三、lock 文件要不要入库：看项目类型

这是依赖治理里最容易被做错的一步。

  • 应用项目：lock 必须入库。 npm 官方明确说 package-lock.json「is intended to be committed into source repositories」，目的是让团队、部署和 CI 保证安装完全相同的依赖；Cargo 官方同样建议「when in doubt, check Cargo.lock into the version control system」。
  • 库 / SDK：可以不入库（或发布时再固定），因为库的使用方有自己的依赖解析；但 CI 应该测试多个版本组合，避免「只在我锁的版本上能跑」。
  • 工具链依赖也要锁：CI 里用的 linter、格式化工具、编译器版本同样会漂移，应固定版本（工具链文件、toolchain 指令、固定版本号安装）。

配套做法：CI 使用冻结安装（npm 的 npm ci、pnpm 的 --frozen-lockfile、yarn 的 --immutable），当 package.json 与 lock 不一致时直接失败，而不是默默重新解析——这样能防止「本地改了依赖没提交 lock」。

四、自动化更新：让升级成为常规动作

lock 把版本固定住，但固定不等于冻结。依赖会老化：出现漏洞、停止维护、被弃用。长期不升级，最后要么被迫做一次风险巨大的「大版本跳跃」，要么一直带着已知漏洞。

解决思路是让升级高频、小步、可回滚，而不是一次性大工程：

  • Dependabot（GitHub 官方）：自动提交依赖升级 PR，可与 CI 配合，PR 过测试再合；
  • Renovate（开源）：功能类似，支持多平台多语言、可配置调度与分组，还能对弃用依赖给出迁移 PR。

策略上建议分级：

  • patch：过 CI 即可合，风险最低；
  • minor：看变更说明 + CI，谨慎合；
  • major：SemVer 约定是「不兼容变更」，必须人工评估迁移成本。

关键原则：升级不是目的，可控才是。开自动升级 PR，但每个 PR 都要过 CI、都要有人看，避免「无脑升级」把破坏性变更直接带进主干。

五、供应链安全：漏洞与 SBOM

依赖治理还有安全一面。第三方依赖是攻击面：可能带有已知漏洞，也可能被投毒、被篡改。

  • 漏洞扫描：Node 生态有 npm audit；Go 有官方的 govulncheck，它基于官方漏洞数据库，只报告「你的代码实际调用到的」漏洞函数，噪声较低；这些数据多采用 OSV 格式，便于跨工具使用。
  • 完整性校验：lock 文件里的 integrity 字段（npm 用 sha512/sha1 的 SRI 值）用于校验下载内容未被篡改；对发布物，还可以引入来源证明（provenance / 签名）。
  • SBOM（软件物料清单）：生成一份标准化的依赖清单，便于审计与合规（可参考 SPDX 规范）。
  • 最小化依赖：新依赖要有评审——它是否维护良好、体积多大、是否与现有依赖重复；AI 尤其喜欢「顺手加个库」，这条要写成团队规则。

六、常见反模式

  • lock 进 .gitignore / 从不提交：等于放弃可复现性。
  • 版本范围过宽（*、latest）：把兼容性赌注押在别人身上。
  • 只升不审：自动升级 PR 不看变更、不看 CI 就合。
  • 永远不升：lock 长期不更新，漏洞与废弃越积越多。
  • 忽略传递依赖：只审直接依赖，漏洞往往在传递依赖里。
  • 本地改依赖不提交 lock：没有冻结安装，CI 静默重新解析。

七、落地清单

  1. 确认 lock 文件入库，并在 CI 用冻结安装（npm ci / --frozen-lockfile / --immutable）。
  2. 版本声明用合理范围（^ / ~），不要 *；精确版本交给 lock。
  3. 高要求场景使用锚点：vcpkg builtin-baseline、git 依赖的 rev、必要时 vendor/。
  4. 开启 Dependabot 或 Renovate，按 patch / minor / major 分级处理升级 PR。
  5. 接入漏洞扫描（npm audit、govulncheck）与 SBOM 生成。
  6. 把「新依赖需要评审」写进团队规则——尤其是 AI 生成代码引入的依赖。
