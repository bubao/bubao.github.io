MySQL 升级后认证插件故障排查

在使用 Arch Linux 进行日常滚动升级（pacman -Syu）或在生产环境中将 MySQL 升级至 8.4 LTS 或 9.0+ Innovation 版本后，很多基于 PHP（WordPress/Laravel）、旧版 Node.js、Python 或旧版 Navicat 的业务服务突然发生大面积连接崩溃，服务端日志赫然抛出以下经典致命异常：

为什么升级前运行良好的数据库，在版本号一跃之后连认证插件都找不到了？

本文将还原此次事故的底层演化逻辑，提供立即可用的救急方案（临时开启旧插件）与面向未来的正道方案（升级客户端驱动与无缝平移到 caching_sha2_password），并拆解跨版本认证加密的演进脉络。

一、事故根因：MySQL 官方认证体系的历史大迁徙

要理解为什么会报 Plugin 'mysql_native_password' is not loaded，我们先来看一张 MySQL 默认身份验证插件的版本演进时间线：

1. 为什么 Arch Linux 用户最先踩雷？

Arch Linux 采用的是最激进的 滚动发行模式（Rolling Release）。当上游 MySQL 发布 8.4 LTS 或 9.0 新版时，Arch 的软件仓库会在几天内甚至几小时内同步推送最新二进制。执行 pacman -Syu 后，服务器直接被一脚踹入了新世界。

2. 为什么会抛出 1524 错误？

升级后，服务端的 MySQL 已经不再默认装载 mysql_native_password 动态链接库。但你在数据库老表 mysql.user 中为应用创建的用户，其 plugin 字段依旧记录着历史旧值：

当客户端（如 PHP mysqli、老版 mysql 驱动）发起 TCP 连接握手时，MySQL 服务端在内存中找了一圈，发现根本没有加载名为 mysql_native_password 的认证插件，便毫不客气地丢出了 1524 Plugin 'mysql_native_password' is not loaded 阻断连接！

三、方案二：面向未来的长效正解——全面升级至 caching_sha2_password

重新打开旧插件只是技术负债的延期。mysql_native_password 基于 1995 年代落后的单轮 SHA-1 散列算法，在现代算力下已被证实极易遭受彩虹表碰撞。官方在 MySQL 9.x 中已经彻底清空该插件，未来升级依然必死无疑。

最规范的做法是将数据库用户无缝升级为现代业界标准的 caching_sha2_password，并升级客户端驱动。

2. 客户端驱动适配与升级清单

把数据库用户改成 caching_sha2_password 后，各语言的客户端驱动需要确保符合如下最低版本要求：

① PHP 生态

  • 核心依赖：确保 PHP 安装并启用了 mysqlnd（MySQL Native Driver） 扩展，而非古早的 libmysqlclient；
  • PHP 版本：PHP 7.4+、PHP 8.0+ 的 pdo_mysql 和 mysqli 在搭配 mysqlnd 时天然支持 caching_sha2_password。

② Node.js 生态

  • 避免使用已停止维护的 mysql 库（npm install mysql 默认包早已不维护且不支持现代密码学握手）；
  • 无缝迁移至 mysql2：mysql2 API 与老版完全兼容，但内置了完整的 RSA 公钥置换与 caching_sha2_password 驱动。

③ 数据库客户端工具（Navicat / DBeaver / DataGrip）

  • Navicat：Navicat 11 及更早版本不支持 caching_sha2_password，会报 2059 - Authentication plugin 'caching_sha2_password' cannot be loaded，建议升级至 Navicat 15+ 或改用跨平台开源的 DBeaver、TablePlus。

四、升级后的经典连带暗坑：Public Key Retrieval is not allowed

为什么会出现这个错误？

caching_sha2_password 为了防止密码哈希在网络明文传输中被嗅探，规定：

  • 如果连接开启了 SSL/TLS 加密，直接通过 TLS 隧道安全传输明文密码；
  • 如果连接未启用 SSL，客户端必须向服务端索要公钥（RSA Public Key），用服务端的公钥把密码加密后再发往服务端。
  • 出于安全防中间人（MITM）考虑，客户端驱动默认禁止向未受信任的未知服务端随意索要公钥！
