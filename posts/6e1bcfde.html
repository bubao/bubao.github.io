RKNN 量化与部署调优

上一篇讲了 RK35xx 的硬件流水线，这一篇聚焦 NPU 上的关键一步：怎么把模型变成 .rknn 并跑出该有的性能。很多人第一次部署会遇到两个典型问题——精度比 PyTorch 差一截，或者速度远低于预期。这两个问题大多不是 NPU 不行，而是量化与部署环节的配置没对齐。

本文按工具链流程走：量化 → 转换参数 → 部署调优 → 性能评测，最后给常见问题清单。

一、工具链全流程

RKNN 工具链分为两段：PC 端转换（x86 Linux，做量化与图优化）和板端运行时（ARM，加载 .rknn 推理）。

flowchart LR
    A["原始模型
ONNX / PyTorch / TF"] --> B["rknn-toolkit2
量化 / 图优化"]
    B --> C[".rknn 模型"]
    C --> D["板端 runtime
librknnrt"]
    D --> E["rknn.init / inference
查询与后处理"]

PC 端负责把浮点模型转成 NPU 可执行的定点模型；板端只负责加载与推理。两端的版本要匹配，混用版本是「加载失败」「结果异常」的常见来源。

二、量化：为什么与怎么做

NPU 的乘加单元通常面向定点运算设计，浮点模型必须量化为低比特整数（常见 INT8）才能发挥算力。量化的收益是内存占用、带宽和功耗同步下降；代价是精度可能损失。

工具链主要支持 PTQ（训练后量化）：不需要重新训练，用一批代表性数据做统计，逐层确定量化参数。要点：

  • 量化数据集要代表真实分布：数据太少或分布偏移，量化参数就会失真，精度明显下降；
  • 不是所有层都适合量化：对误差敏感的网络（如某些注意力、小目标检测头）可能需要保留更高精度，工具链通常支持混合精度/部分层不量化；
  • 精度对齐顺序：先确认浮点模型本身没问题，再做量化，最后对比量化前后在同一批数据上的指标，避免把训练问题误判为量化问题。

三、转换参数与精度对齐

转换时的配置直接决定结果，几个关键项：

参数作用常见错误
输入尺寸决定推理分辨率与预处理尺寸不一致，坐标映射错位
归一化（mean/std）把像素值映射到模型期望范围漏配或配反，结果整体异常
通道布局NHWC / NCHW与训练时不一致，精度暴跌
动态尺寸允许变分辨率输入不是所有模型都支持，超范围会失败

另外要确认算子支持：NPU 只原生支持一部分算子，不支持的算子会回退到 CPU 执行。回退本身能跑，但会在硬件链路里插入一段 CPU 计算，性能往往断崖式下降。转换工具一般会给出支持情况，务必在转换阶段就看清楚。

四、部署调优

1. NPU 核心与并发

RK3588 的 NPU 为多核心设计，RK3566 这类为单核。多模型并发时：

  • 多核平台可由运行时把不同模型调度到不同核心；
  • 单核平台只能靠请求合并、批量推理、错峰调度提高利用率；
  • 并发不是越多越好，超出 NPU 能力后排队只会增加延迟。

2. 内存与零拷贝

  • 输入输出缓冲区复用，避免每次推理都申请释放；
  • 与解码、RGA 衔接时走 DMA-BUF 共享内存（见上一篇），把预处理也留在硬件链路里；
  • 内存占用过高会挤压系统其它模块，边缘设备尤其明显。

3. 批量与延迟的取舍

批量推理能显著提升吞吐，但会引入排队延迟。实时交互场景优先低延迟，离线批处理优先高吞吐，按业务目标选。

五、性能评测与瓶颈定位

  • 转换阶段：用工具链自带的评测能力，对比不同量化配置的精度与耗时；
  • 板端阶段：测单帧推理耗时、连续推理吞吐、NPU 利用率；
  • 定位顺序：先确认模型本身耗时（PC 端），再确认板端运行时耗时，最后看数据链路是否拖后腿；
  • 若板端远慢于 PC 端评测，优先怀疑输入输出拷贝、CPU 回退算子、缓冲区未复用。

六、常见问题

问题可能原因处理方向
精度明显下降量化数据不具代表性、归一化/布局错误换代表性数据重量化、核对转换配置
速度远低于预期算子回退 CPU、逐帧拷贝、缓冲区未复用查算子支持、走零拷贝、复用内存
加载失败工具链与运行时版本不匹配统一 toolkit2 与 librknnrt 版本
结果坐标/尺寸异常输入尺寸或通道布局不一致核对预处理与转换参数
多路并发卡顿NPU 吞吐不足、请求堆积减路数、加批量、错峰调度

七、总结

  • 先确认浮点模型正确，再谈量化与部署；
  • 量化数据集、归一化、通道布局是精度对齐的三要素；
  • 算子支持情况决定性能上限，务必在转换阶段确认；
  • 部署调优的核心是减少 CPU 参与：多核调度、内存复用、零拷贝；
  • 性能问题按「模型 → 运行时 → 数据链路」顺序定位。
