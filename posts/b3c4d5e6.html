Nginx 工程实践 -- 23. CORS 跨域配置

前后端分离、第三方嵌入、本地开发联调，都会撞上浏览器的同源策略。CORS 的响应头谁都能加，但预检（OPTIONS）怎么处理、带凭证时 * 为什么失效、Vary 为什么必须加，这些细节一错就是"浏览器报 CORS 错误、后端日志却一片正常"。

一、简单请求与预检

浏览器把跨域请求分两类：

  • 简单请求：方法为 GET/HEAD/POST，且头字段在安全列表内（如 Accept、Content-Type: application/x-www-form-urlencoded 等），直接发送，响应头里带 Access-Control-Allow-Origin 即可；
  • 预检请求：用了 PUT/DELETE、自定义头、application/json 等情况，浏览器先发 OPTIONS，等 Nginx 返回允许的方法/头/来源后，才发真正的请求。

所以 Nginx 侧要做两件事：响应加 ACAO，以及处理 OPTIONS 预检。

二、响应加 CORS 头

  • always 很重要：默认 add_header 只在 200/201/204/206/301/302/303/304/307/308 时生效，4xx/5xx 不带；CORS 头要在错误响应上也存在，否则浏览器仍拦截；
  • Access-Control-Allow-Origin 用 $http_origin 回显来源（动态），或按需写白名单变量（见下）。

六、常见坑

坑说明
响应头不加 always错误响应没有 CORS 头，浏览器仍拦截
带凭证用 *浏览器直接拒绝，必须回显具体来源
没处理 OPTIONS预检 405/404，真实请求从不被发出
动态 Origin 没加 Vary缓存串味，不同来源拿到错误头
if 里 proxy_passif 内推荐 return/rewrite，别做复杂逻辑（见第 14 篇）
来源白名单写死用 map 收敛，避免正则散落
只在 server 加头注意 add_header 的继承覆盖规则（子级定义会覆盖父级同名头）

小结

  • 简单请求只需 Access-Control-Allow-Origin；预检要先答 OPTIONS；
  • add_header ... always 保证错误响应也带 CORS 头；
  • 带凭证时 * 失效，必须回显具体来源 + Allow-Credentials；
  • 动态 Origin 必须加 Vary: Origin；
  • 来源白名单用 map 收敛，if 里只做 return。
