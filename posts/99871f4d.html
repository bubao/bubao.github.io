Windows 平台 Node.js 实现文本转语音 TTS

在日常开发服务端工具、自动化脚本或本地 CLI 工具时，我们经常有让程序“开口说话”的需求：

  • 长时间运行的打包编译或数据爬虫任务完成时，发出语音通知；
  • 本地守护进程监控到异常告警时，播报即时警报；
  • 在完全离线、无外网连接的局域网或保密机房中，无法调用商业云厂商（如阿里云、腾讯云、Azure）收费且必须联网的 TTS API。

很多开发者第一时间会想到引入基于 Python 的 pyttsx3，但这需要客户端预先安装 Python 运行环境；或者尝试安装一些 npm 上的 C++ 语音扩展包，却经常在 node-gyp 和 Visual Studio 编译环境前频频受挫。

其实在 Windows 生态下，操作系统底层早已内置了非常成熟的语音合成引擎（SAPI / .NET System.Speech）。我们只需在 Node.js 中通过轻量子进程管道与系统内置的 PowerShell 协同，就能做到零第三方笨重依赖、完全离线、毫秒级启动的原生文本转语音（TTS）播报。

二、底层拆解：代码究竟是如何跑通的？

这段看似小巧的代码背后，实际上巧妙地串联了三个维度的系统能力：

1. 动态加载 .NET System.Speech 运行时

PowerShell 作为 Windows 现代自动化外壳，拥有与 .NET 框架天然互通的能力。

  • Add-Type -AssemblyName System.speech;：指示 CLR 在运行时直接加载全局程序集缓存（GAC）中的 System.Speech.dll；
  • New-Object System.Speech.Synthesis.SpeechSynthesizer;：实例化核心语音合成器对象。该对象底层直接调用 Windows 系统的 SAPI（Speech Application Programming Interface），拥有对本地已安装语音库的完全调度权。

2. 关键参数调节

  • $speak.Rate：控制语速，取值范围为 -10（极慢）到 10（极快），0 为标准自然语速；
  • $speak.Volume：控制播放音量，取值范围为 0 到 100；
  • $speak.Speak(...)：执行同步语音合成与发声。

然而这会导致语音播报变成一连串不知所云的乱码杂音，甚至系统直接哑火！

根因深度剖析：Windows 默认控制台代码页（CP936）

  • Node.js 端：内部所有字符串在流式传输时，默认使用 UTF-8 字节编码；
  • Windows PowerShell 端：在绝大多数简体中文 Windows 系统中，控制台默认代码页是 CP936（GBK / GB2312）；
  • 当 PowerShell 通过 [Console]::In.ReadLine() 读取标准输入流时，会按照系统的本地默认编码（GBK）去解析传入的字节流；
  • UTF-8 的多字节中文字符被强行按双字节 GBK 解码，直接导致严重的乱码错位（如“浣犲ソ”乱码），语音引擎解析到的完全是一串无意义的生僻字！

七、总结

在特定技术场景下，最优雅的解法往往不是盲目引入数百兆的重型运行时或花费昂贵的第三方云服务，而是充分挖掘操作系统自带的原生基础设施。

通过 Node.js 与 Windows .NET System.Speech 的跨进程轻量级握手，并妥善解决编码与流控制问题，我们以极低的代码成本实现了高可用、完全离线、毫秒级响应的工业级文本转语音管道。
