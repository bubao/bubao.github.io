Nginx 工程实践 -- 24. 安全基线：版本指纹与 WAF

第 6 篇覆盖了限流与响应头，第 7 篇覆盖了 TLS。这篇补上"暴露面收敛"的另一半：别让对手知道你用的是哪个版本，以及在网关前面加一层攻击特征检测。两者都不需要改应用，却是安全基线里性价比最高的两步。

flowchart TD
    A["请求"] --> B["Nginx
server_tokens off"]
    B --> C{"WAF / 规则"}
    C -->|"命中攻击特征"| D["拦截 / 403"]
    C -->|"正常"| E["转发后端"]
    F["error_log"] --> G["fail2ban 封禁 IP"]
    G --> H["防火墙规则"]

一、收敛版本指纹

Nginx 默认会在错误页和 Server 头里暴露精确版本号，给攻击者按版本查 CVE 的便利。

  • server_tokens off 只影响错误页和 Server 头里的版本号（仍会显示 nginx）；
  • 想去掉 Server: nginx 这个标识，需要第三方 headers-more 模块的 more_clear_headers Server;；
  • 同理，X-Powered-By 常由后端（PHP/Express 等）输出，要么后端关，要么用 more_clear_headers / proxy_hide_header 抹掉。

二、保护敏感入口

管理端口、状态页、内部接口一旦暴露，等于把监控送给攻击者：

  • stub_status 必须配 allow/deny 或 auth_basic；
  • 管理接口尽量只监听内网回环，不对外。

三、WAF：在网关前加一层特征检测

Nginx 自身不做攻击特征识别，需要外挂 WAF。常见两条路：

1. ModSecurity + LibModSecurity（开源）

  • 基于 OWASP CRS 规则集，覆盖 SQL 注入、XSS、路径穿越等；
  • 代价是性能开销与误报调优，建议先 SecRuleEngine DetectionOnly 观察，再开启拦截。

2. 商业 WAF / 云 WAF

把流量先过 WAF 再到 Nginx，Nginx 只负责回源与访问控制。

无论哪种，都要注意：

  • WAF 规则要持续更新，否则形同虚设；
  • 开启前先观察模式（DetectionOnly）统计误报；
  • 对静态资源、健康检查路径可降级或跳过，减少开销。

四、与限流、封禁的联动

Nginx 的 error_log 是封禁系统的输入。典型组合：

  • error_log 里记录 403/404/异常频率（第 11 篇）；
  • fail2ban 读取日志，超过阈值调用 iptables/nftables 封 IP；
  • 限流（第 6 篇）作为第一道，封禁作为处置手段。

五、常见坑

坑说明
只关 server_tokens只隐藏版本号，Server: nginx 仍在
状态页对外stub_status 泄露连接数、请求量等信息
WAF 直接开拦截误报会拦正常用户，先 DetectionOnly
规则不更新WAF 形同虚设
依赖 X-Forwarded-For 封禁伪造头会封错 IP，先用 real_ip 还原（第 4 篇）
全部流量都过 WAF静态/健康检查可绕过，降低开销

小结

  • server_tokens off 隐藏版本号，more_clear_headers Server 去掉标识；
  • 抹掉 X-Powered-By 等后端指纹；
  • 状态页/管理入口必须 allow/deny 或 auth_basic；
  • WAF 先 DetectionOnly 再拦截，规则持续更新；
  • error_log + fail2ban + 防火墙做联动封禁。
