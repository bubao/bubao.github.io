Git 批量修改历史提交的作者与邮箱

在日常团队协作或个人开源项目维护中，我们几乎都遇到过提交身份信息配置错误的尴尬情况：

  • 在新搭建的开发机或服务器上克隆仓库后，忘记执行 git config --global user.email，导致大量提交直接带上了机器名 root@localhost 或系统默认用户名；
  • 在个人电脑上开发公司业务代码时，不慎混用了个人的私有 GitHub 邮箱；
  • 准备将私有项目脱敏后开源发布时，发现早期历史记录中残留了公司内网专属邮箱或前同事的敏感身份标识。

由于 Git 内部采用哈希链表结构，提交者的姓名与邮箱直接参与了 Commit Hash（校验和）的哈希计算。修改历史提交信息意味着重写从该提交之后的所有 Commit 节点。

本文将由浅入深，分别讲解使用经典脚本 git filter-branch 与新一代官方推荐工具 git-filter-repo 批量重写 Git 历史作者信息的实操方案，并探讨团队协作中的推送注意事项。

一、Git 提交身份的双重属性：Author 与 Committer

在开始修改前，我们需要先明确 Git 内部记录的两个关键身份字段：

  1. Author（作者）：实际编写这段代码的人。即便后续代码被他人 cherry-pick、rebase 或以补丁形式应用，Author 仍保持不变。
  2. Committer（提交者）：最终将这段代码合并或应用到当前分支仓库的人。

在常规单人提交时，Author 与 Committer 通常是同一人；但在执行 rebase、merge、cherry-pick 等操作后，二者可能会分离。因此在批量替换时，我们需要同时判定并修改这两个字段，确保历史记录彻底整洁一致。

2. 参数关键点剖析

  • --env-filter：针对每一个提交遍历执行的环境变量过滤器。我们通过重置 GIT_AUTHOR_NAME、GIT_AUTHOR_EMAIL、GIT_COMMITTER_NAME、GIT_COMMITTER_EMAIL 四个环境变量来覆写提交元数据。
  • --tag-name-filter cat：在重写提交对象时，自动重新将对应的 Tag 标签指向新的提交 Hash，保持标签引用有效。
  • -- --branches --tags：双横线表示后续参数为引用范围，指定对本地所有的分支（branches）和标签（tags）同时生效，防止遗漏某些未 checkout 的分支。

五、推送到远端与团队协同避坑指南

无论是 git filter-branch 还是 git-filter-repo，本质上都改变了历史 Commit 的 Hash 散列值。因此，将修改后的结果同步到远端仓库时，需要特别谨慎：

2. 协作者如何同步（关键避坑）

如果团队里其他成员直接执行 git pull，Git 默认会将本地的旧提交与远端的新提交进行合并（Merge），这会导致被修正的旧提交再次复活并被合入主干，导致整个修改前功尽弃！

六、总结

工具 / 命令适用场景优势注意事项
git commit --amend仅改动最近 1 次提交简单快捷，无副作用仅限单一叶子节点
git rebase -i改动最近数次提交精细可控，无需外部依赖节点较多时操作繁琐
git filter-branch批量历史整改原生内置，环境开箱即用较慢，官方已逐步弃用
git-filter-repo批量大型仓库重写极速、安全、支持 mailmap需独立安装 Python 依赖

在执行任何批量重写操作之前，请务必对当前仓库进行完整本地备份（如直接复制一份 .git 目录），确保操作具备可撤销的回退保障。
