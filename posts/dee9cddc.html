YOLO 任务类型与选型

很多人第一次接触 YOLO，会问「YOLOv8 和 YOLO11 选哪个」「n 和 s 差多少」。但这些问题都跳过了更前面一步：你要模型输出什么。YOLO 不是「一个模型」，而是一族模型；同一代架构下，官方提供了检测、分割、姿态、分类、旋转框五种任务类型，它们的输出结构完全不同，选型时先错任务类型，后面调参、换尺寸、换版本都是在错误的方向上使劲。

本文把选型拆成三个正交的维度：任务类型（输出什么）、模型尺寸（多大算力）、模型版本（哪一代架构），并给出按需求决策的顺序。

一、三个正交的维度

维度取值决定什么
任务类型detect / segment / pose / classify / obb模型输出什么结构
模型尺寸n / s / m / l / x参数量、显存、推理延迟、精度上限
模型版本YOLOv5 / YOLOv8 / YOLO11 等架构代际、算子支持、生态成熟度

三者是正交的：YOLO11 有 yolo11n 到 yolo11x 五个尺寸、五种任务；YOLOv8 同样如此。所以「选 YOLO11s」其实只说清了两个维度，还差任务类型。

二、五种任务类型分别输出什么

任务输出典型场景什么时候选
detect（检测）矩形框 + 置信度 + 类别定位、计数、存在性判断绝大多数场景的默认起点
segment（分割）矩形框 + 掩码（轮廓）面积、边缘、抠图、缺陷区域需要知道「形状和范围」，而不只是「有没有」
pose（姿态）框 + 关键点坐标姿态识别、动作合规、工位检测关注的是关键点之间的相对位置
classify（分类）整图类别概率整图判定、场景识别、合格/不合格不需要位置，只需要「这张图是什么」
obb（旋转框）旋转矩形（中心、宽高、角度）航拍、遥感、斜放目标、料框目标方向任意、紧贴的旋转框更贴合

几个关键点：

  • detect 的框是轴对齐矩形，对倾斜目标会带入大量背景，且框与框之间重叠严重；
  • segment 的掩码是逐像素的，能给出轮廓与面积，但推理成本更高，计数场景用它属于「杀鸡用牛刀」；
  • classify 不输出位置，无法回答「在哪里」，只能回答「是什么」；
  • obb 输出的是旋转框，对航拍、电路板、堆叠物料这类方向不固定的目标，标注和评估方式都不同。

三、按需求选任务类型

flowchart TD
    Q0{"需求要输出什么?"}
    Q0 -->|"只要整图类别"| C["classify"]
    Q0 -->|"要位置"| Q1{"要轮廓或面积?"}
    Q1 -->|"要"| S["segment"]
    Q1 -->|"不要"| Q2{"要关键点?"}
    Q2 -->|"要"| P["pose"]
    Q2 -->|"不要"| Q3{"目标方向任意或倾斜?"}
    Q3 -->|"是"| O["obb"]
    Q3 -->|"否"| D["detect"]

决策顺序建议：先看输出结构，再看是否需要位置，最后看几何形态。需求不清晰时，先用 detect 把流程跑通——它是最通用、资料最多、部署支持最好的一档，后续发现需要轮廓或关键点，再换任务类型，改动的是模型与训练数据，不是整个流程。

常见的选型误区：

  • 用 detect 去做「缺陷面积占比」，框无法表达形状，应换 segment；
  • 用 segment 去做「传送带上计数」，掩码开销换不来业务价值，detect 就够；
  • 用 classify 去找「哪个工位有问题」，没有位置信息，应换 detect 或 pose；
  • 检测目标倾斜、密集排列（如航拍车辆），detect 的轴对齐框重叠严重，应考虑 obb。

四、任务内选模型尺寸

同一任务下，n/s/m/l/x 的差别是参数量与计算量，对应精度上限与推理延迟。以 YOLO11 为例，官方给出的参数量从 n 到 x 跨越一个数量级以上（约 2.6M 到 56.9M），FLOPs 从约 6.5G 到 195.4G（来源：Ultralytics YOLO11 模型页）。选择原则：

场景建议
边缘设备（树莓派、NPU）n / s，优先保证帧率
服务端 GPU 实时s / m，精度与延迟平衡
离线批处理、精度优先l / x，延迟不敏感
目标极小、极密集更大尺寸 + 更大输入分辨率，但要同步评估延迟

尺寸不是越大越好：小模型 + 干净数据往往比大模型 + 脏数据更实用。先用 n 验证任务是否可解，再按需往上加。

五、版本选择：追新还是求稳

YOLOv8 与 YOLO11 都是官方维护的架构。YOLO11 引入了 C3k2 块与 C2PSA 注意力机制，官方称在更少参数下取得更高精度（来源：YOLO11 发布说明）。但版本选择的现实约束是部署生态：

  • 训练框架、数据标注、社区资料：v8 更成熟；
  • 导出格式支持（NCNN、RKNN、OpenVINO 等）：以所用部署引擎的支持为准，新架构不一定第一时间适配；
  • 项目已跑通的链路：没有明确收益时，不轻易换代。

选型顺序建议：输出什么 → 任务类型 → 尺寸 → 版本 → 导出格式。版本和导出格式属于工程约束，应该最后确认，而不是最先纠结。

六、总结

  • 任务类型由输出结构决定，是选型的第一问；
  • 尺寸由算力与精度决定，先小后大；
  • 版本由生态与部署支持决定，求稳优先；
  • 需求不清时从 detect 起步，避免一开始就为边缘需求过度设计。
