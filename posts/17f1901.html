npm 发包完整实践与避坑指南

不久前在维护一个跨项目通用的底层算法库时，需要将其独立打包发布到 npm 官方公有仓库（如 @scope/pkg 或独立包）。虽然平时也有零星的发包经验，但由于流程未做标准化沉淀，实际操作时很容易踩入一系列隐蔽暗坑：

  • 命令行登录遭遇 403 Forbidden 与 Cloudflare / 2FA 阻断；
  • package.json 中的 version 与 Git Tag 脱节，难以回溯追溯历史；
  • 误把未编译源码、测试用例或敏感环境文件推向公网镜像；
  • 现代前端生态下，打包出的产物无法同时兼顾 ESM 与 CommonJS（Dual Package Hazard）；
  • 踩中 npm 极其严苛的 “24 小时禁止重复发布同名版本” 撤包惩罚机制。

本文将结合多次开源发包排坑经历，系统梳理一套现代 npm 发包的标准化工作流、工程配置与避坑救砖指南。

二、现代构建与模块导出：攻克 ESM 与 CJS 双模块兼容

现代前端与 Node.js 社区最大的痛点之一，就是 CommonJS（CJS） 与 ECMAScript Modules（ESM） 的生态撕裂。一个设计良好的 npm 包应当做到让使用者无论是 import 还是 require 都能开箱即用，并且提供完备的 TypeScript .d.ts 类型定义。

📌 核心避坑细节：

  1. exports 中的 types 顺序：types 必须放在 import 和 require 的最前面，否则 TypeScript 编译器解析时可能命中后面的 js 字段而忽略类型声明；
  2. sideEffects: false：声明该库无副作用，能够让 Webpack、Rollup、Vite 等上层打包工具进行彻底的 Tree-shaking（摇树优化）；
  3. files 严格白名单：杜绝将 src/ 源码、本地测试用例、未忽略的 .env 敏感文件推到公网镜像。

三、版本管理：npm version 与 Git Tag 联动机制

发布开源包最忌讳的是 package.json 的版本号与 Git 仓库的 Commit、Tag 割裂脱节。手动修改文件、手动 git commit、再手动打 tag 极易出现人为遗漏。

npm 原生内置的 npm version 命令可以一键完成三件事：

  1. 更新 package.json（及 package-lock.json）的版本号；
  2. 自动生成一条版本变更的标准 Git Commit；
  3. 在本地 Git 仓库打上对应版本的 Git Tag。

npm 官方的“后悔药”限制规则（源自 left-pad 事件）

为了防止破坏全球 Node.js 社区的依赖树完整性（著名的 left-pad 下架导致全网构建瘫痪事件），npm 制定了极度严苛的撤包政策：

  1. 时间限制：只有发布后 24 小时以内 的包允许 unpublish；
  2. 依赖限制：如果该包已被任何其他公开包声明为依赖，禁止 unpublish；
  3. 版本黑名单机制（最关键）：任何被删除过的版本号（如 0.0.3）将永远作废！你无法通过重新发布覆盖一个已经存在过或删除过的版本！

如果代码确实发错了，千万不要试图删除重发，标准的行业救砖方案为：
