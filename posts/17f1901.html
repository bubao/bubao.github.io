npm 发包完整实践与避坑指南

不久前在 GitHub 上给“雪花漂移算法（Snowflake ID）”的原作者提交了一个 PR，由于原作者迟迟未合并且原项目并未发布独立的 npm 包，为了方便自己在多个项目中直接开箱引用，便打算将其打包整理并发布到 npm 官方仓库（如 cherry-id）。

虽然之前也有过发包经验，但平时大多零散操作未做系统记录。这次实际发布过程堪称一波三折——从命令行登录 403 拦截、Git Tag 与版本号脱节，再到踩中 npm 极其严苛的撤包（unpublish）惩罚机制。本文将结合这次发包经历，系统梳理一套现代 npm 发包的标准化工作流与避坑指南。

  2. 现代化 2FA / WebAuthn 验证：
    现阶段 npm 官方全面启用了双因素认证（2FA）。现代 npm CLI（Node.js >= 18）在执行 npm login 时，会自动在终端打印一次性验证码并在浏览器打开登录授权页面，授权通过后本地会自动获得带时效的 Token。

二、版本控制：npm version 与 Git Tag 联动

发布开源包时，最忌讳的是 package.json 中的 version 字段与 Git 仓库的 Commit、Tag 割裂。手动去修改文件、手动提交再手动打 Tag 极易遗漏。

npm 原生内置了极其优雅的 npm version 命令，支持一键完成三件事：

  1. 更新 package.json（及 package-lock.json）的版本号；
  2. 自动生成一条版本变更的 Git Commit；
  3. 在本地 Git 仓库创建对应版本的 Git Tag。

npm 官方的“后悔药”限制规则（源自 left-pad 事件）

为了防止破坏全球 Node.js 社区的依赖树完整性（著名的 left-pad 下架导致全网构建瘫痪事件），npm 制定了极度严格的撤包政策：

  1. 时间限制：只有发布后 24 小时以内 的包允许 unpublish；
  2. 依赖限制：如果该包已被任何其他公开包声明为依赖，禁止 unpublish；
  3. 版本黑名单机制（最关键）：任何被删除过的版本号（如 0.0.3）将永远作废！你无法通过重新发布覆盖一个已经存在过或删除过的版本！
