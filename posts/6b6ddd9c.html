Node.js 批量文件下载实战

在日常服务端与全栈开发中，“批量下载文件”是一个极其普遍的业务诉求：抓取爬取图片、离线同步静态资源、备份第三方媒体文件等。

初学者往往认为这很简单：“不就是写个 for 循环，发个 HTTP 请求拿到数据然后 fs.writeFileSync 吗？”

然而，一旦进入海量文件（如数千张图片）或大文件（如数百兆视频/压缩包）的生产场景，这种初级写法会引发一系列灾难：

  1. 内存爆仓（OOM）：全量 Buffer 读入内存，V8 垃圾回收停顿甚至直接崩溃；
  2. 并发失控：无脑 Promise.all 瞬间并发数千个 TCP 连接，触发本地 EMFILE: too many open files 错误，同时直接被对方服务端防护判定为 DoS 攻击并封禁 IP；
  3. “假完成”隐形 Bug：对原生 Stream 误用 await stream.pipe(...)，程序以为下载完成，实则底层网络流还在传输或已悄然静默中断；
  4. 脏数据碎片残留：网络抖动或中途报错导致磁盘上残留大量只有几 KB 的半截文件，系统无法区分哪些是完好数据。

本文将从底层 Node.js 管道流式传输、滑动窗口并发池、临时原子重命名到指数退避重试，全方位打造一个高可靠、工业级的批量下载引擎。

最佳实践：

  1. 始终先下载写入临时文件：targetPath + '.tmp'；
  2. 整个 Stream 管道成功落盘并关闭后，调用 fs.promises.rename 原子性地重命名为正式目标路径；
  3. 一旦下载报错，捕获异常并主动安全清除 .tmp 临时碎片。

六、进阶架构思考：生产调优要素

  1. HTTP Keep-Alive 连接池复用：在频繁请求相同域名（如某 CDN 图床）时，默认创建新的 TCP 握手与 TLS 协商非常昂贵。可通过在 got 或原生 fetch 中配置自定义 http.Agent 与 https.Agent，开启 keepAlive: true 和设置合理的 maxSockets，显著降低连接握手延迟。
  2. 大文件断点续传（HTTP Range Header）：针对体积数 GB 的超大文件，若在 95% 时因网络断开重新从头下载极不合理。可在请求头中附带 Range: bytes=${currentSize}-，仅向服务端请求缺失部分并以追加模式（fs.createWriteStream(tmpPath, { flags: 'a' })）写入。
  3. 磁盘 I/O 吞吐与背压调节：使用 stream/promises.pipeline 的最大价值在于：当本地磁盘繁忙写缓冲区已满时，它会自动暂停接收网络包，从而杜绝由于网络输入过快把内存撑爆的极端情况。
