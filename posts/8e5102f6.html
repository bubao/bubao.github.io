浅谈 JS 异步

刚从 C 或 Java 转来写 JavaScript / Node.js 的时候，很多人最不适应的就是它的异步机制。在传统的同步思维里，代码严格一行行往下跑，前一行执行完了才走下一行；但在 JavaScript 中，这种直觉常常会被“打脸”。

本文从最基础的困惑切入，系统梳理 JavaScript 异步方案的演进历程：回调函数 $\to$ 事件监听 $\to$ Promise $\to$ async/await，并通俗拆解其背后的执行机制。

二、回调函数就一定是异步的吗？

这里必须澄清一个常见的误区：回调函数（Callback）本身并不等于异步！

在 JavaScript 中，回调函数分为两种：

1. 同步回调

回调函数在当前主线程的执行栈中立即、同步执行完毕，不会排队等待。最典型的就是数组的原生高阶函数：

2. 异步回调

回调函数不会立刻执行，而是被挂起或注册到宿主环境中，等异步事件（网络请求、定时器到期、磁盘 I/O）触发后，才将回调推进任务队列中等待主线程调度：

五、底层原理：为什么异步总是在最后执行？（简说 Event Loop）

很多同学会好奇：如果 setTimeout(..., 0) 延迟设为 0 毫秒，它会比后续的 console.log('end') 先执行吗？

答案是依然在最后执行。这是由 JavaScript 单线程的 事件循环（Event Loop） 决定的：

  1. 单线程执行栈（Call Stack）：浏览器或 Node.js 会优先一口气把当前所有的同步代码全部推入执行栈执行完；
  2. 异步进队列：当遇到 setTimeout 或 I/O 时，宿主环境在后台计时，到期后将回调放进**任务队列（Task Queue）**排队；
  3. 事件循环调度：只有当主线程的执行栈完全清空为空时，事件循环才会去任务队列里把排队的回调捞出来放进执行栈执行。

总结

JavaScript 的异步机制并非刻意刁难开发者，而是单线程语言为了避免“一个网络请求卡死整个网页或服务器”而做出的天才架构设计。

从最初的 Callback 地狱，到 Promise 链式规范，再到如今像写同步代码一样自然的 async / await，理清这套演进脉络与任务调度逻辑，写起复杂业务逻辑便能得心应手。
