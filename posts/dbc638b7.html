Nginx 同时代理静态资源和 API 服务

前后端分离项目交付时，常见需求是在同一个对外端口上完成分发：/ 返回 SPA 打包产物、/api/ 转发给后端服务、/upload/ 直接读服务器上的用户上传文件。三者对 Nginx 的能力要求完全不同：静态要缓存高效，API 要代理转发并保留真实客户端信息，上传目录要兼顾路径映射与体积上限。

一、路由拓扑

注意三处前缀都带尾斜杠：/api/ 与 /upload/ 写成不带尾斜杠会意外匹配 /apixxx、/uploadxxx 这类路径。

三、关键细节拆解

3.1 proxy_pass 的路径拼接（最容易翻车）

proxy_pass 写法客户端请求后端实际收到
proxy_pass http://backend;/api/users/api/users（原样透传）
proxy_pass http://backend/;/api/users/users（剥掉 location 前缀）
proxy_pass http://backend/api/;/api/users/api/users（等价于不写 URI，冗余）

规则：proxy_pass 没带 URI 路径就原样透传；带了路径就把 location 匹配到的前缀替换掉。 后端路由本身就带 /api 时，直接用不带 URI 的写法最不容易错；只有"前缀需要剥离"的场景才写尾斜杠。另外 location /api/ 与 proxy_pass ... / 组合时，/api/（不带后续路径）会被转发成 /，后端需兼容。

3.2 WebSocket 别写死 Connection: upgrade

原文的静态写法：

会把所有请求的 Connection 头都改成 upgrade，普通 HTTP 请求也受影响。正确姿势就是前面的 map $http_upgrade $connection_upgrade：有 Upgrade 头才升级，普通请求为 close。map 只能放在 http 块，不能放 server 里。

3.3 root 与 alias 的分界线

  • root（追加）：location /upload/ { root /var/serverSource; } → root + /upload/ + 文件名，即 /var/serverSource/upload/avatar.png；
  • alias（替换）：location /upload/ { alias /data/uploads/; } → 直接映射到 /data/uploads/avatar.png。

一句话：路径前缀要保留用 root，要去掉用 alias。用 alias 时 location 与 alias 的尾斜杠必须一致，否则 404；改配置后必须 nginx -t && nginx -s reload。

3.4 上传链路：体积与缓冲

  • client_max_body_size 默认 1MB，图片/视频业务必须显式调大；
  • proxy_request_buffering off 让请求体边收边传，后端压力大、Nginx 磁盘压力小，但后端抖动时没有 Nginx 兜底；
  • 保持默认 on 时，Nginx 会把 body 缓冲到临时目录再转发，注意磁盘余量；
  • 后端读取文件后用 Content-Length/Transfer-Encoding: chunked 返回大文件时，给 API 配足 proxy_read_timeout。

3.5 SPA 回退与静态缓存

  • try_files $uri $uri/ /index.html; 是 History 路由刷新不 404 的标准解；
  • 但缺失的 JS/CSS 也会被回退成 index.html（200 + HTML），前端会拿到 MIME 不对的响应；因此给带扩展名的资源单独一个 location，用 try_files $uri =404; 兜底（模板里可选段）；
  • 带内容哈希的构建产物可以 expires 1y；HTML 入口不要长缓存，否则发版后用户可能拿到旧 HTML 引用已删除的哈希资源。

3.6 缓存头只写一次

expires 已经会输出 Expires 和 Cache-Control: max-age，如果再 add_header Cache-Control "public, no-transform"，响应里会出现两个 Cache-Control。二选一：

  • 用 expires 7d;（简单，max-age 自动）；
  • 或 add_header Cache-Control "public, max-age=604800, no-transform";（不加 expires）；
  • 需要同时自定义两者时，装第三方 headers-more 模块的 more_set_headers。

3.7 其他生产建议

  • 安全头：静态与 API 都可加 X-Content-Type-Options: nosniff；SPA 的 HTML 建议按团队规范加 CSP、X-Frame-Options 等；
  • MIME：上传目录最好保持文件扩展名；对可疑扩展（.svg、.html）注意 MIME 与 XSS 风险，必要时强制 Content-Disposition: inline 时先确认来源；
  • 性能：http 块开 sendfile on; tcp_nopush on;，上传/图片目录可开 open_file_cache 缓存文件描述符；
  • API 健壮性：配合 upstream 的 keepalive，调 proxy_next_upstream 应对 502 重试（注意幂等性）；
  • 日志：静态资源关 access_log off 或单独文件，避免高频小图把主日志冲爆（模板中已示例）。

四、验证方法

API 侧重点确认后端拿到的 Host、X-Real-IP、X-Forwarded-For 是否为真实值；前端重点确认预压缩资源 Content-Encoding: gzip 正常。

七、小结

一套配置同时服务三种资源，本质是把三种不同的语义放对位置：静态讲缓存与回退，API 讲透传与超时，上传目录讲体积与安全。proxy_pass 拼路径、WebSocket 升级、缓存头写几次，是最常踩的三个坑；把模板里的注释过一遍，基本就能覆盖 90% 的部署场景。
