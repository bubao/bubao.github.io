PM2 优雅退出与零停机平滑重载实践

在日常 Node.js 服务端开发与部署中，很多人习惯直接使用 pm2 restart app 或者开启 --watch 依赖文件变动自动重启。

但在高并发生产环境中，这种粗暴的重启方式往往是重大生产事故的导火索：正在处理的请求被瞬间腰斩（客户端报 502 / Connection Reset），未完成的数据库事务产生孤儿脏数据，消息队列消费到一半未 ACK 导致死锁或重复投递。

本文将从操作系统信号机制到 Node.js 事件循环底层，系统性拆解 优雅停机（Graceful Shutdown） 与 零停机重载（Zero-Downtime Reload） 的工业级最佳实践。

一、为什么需要优雅退出？生产事故复盘

当我们执行 kill -9 <pid> 或默认重启命令时，操作系统会强制向进程发送 SIGKILL 信号，Node.js 运行时根本来不及执行任何清理逻辑就被瞬间抹杀。

要实现真正的生产级高可用，必须同时满足两个层面的要求：

  1. 应用层面（Graceful Shutdown）：服务实例在收到退出指令时，先拒收新请求，把手上正在跑的请求全部消化干净，再关闭底层依赖资源，最后自尽；
  2. 编排层面（Zero-Downtime Reload）：PM2 在 Cluster 集群模式下采用“滚动更新”策略：先拉起新进程并确认其完全健康就绪（Ready），再将流量切入，最后通知旧进程优雅退出。

二、PM2 的信号机制与关键配置

1. PM2 退出信号传递链路

当我们在终端执行 pm2 reload 或 pm2 stop 时，PM2 内部会触发如下生命周期：

  1. 发送通知信号：PM2 默认向子进程发送 SIGINT（可在配置中修改为 SIGTERM）；
  2. 等待优雅退出：PM2 开启内部倒计时，等待子进程自身执行清理并调用 process.exit(0)；
  3. 超时无情强杀：如果在规定的 kill_timeout 时间内子进程仍未退出，PM2 将直接发送 SIGKILL（强制物理抹杀）。

2. 致命的默认值：1600ms

PM2 默认的 kill_timeout 仅为 1600ms（1.6 秒）！

在稍微复杂的业务中，一个耗时稍长的大报表查询、外部第三方支付网关回调、或者大文件分片写入往往需要 3~5 秒。如果使用默认配置，哪怕你的代码写了优雅停机逻辑，1.6 秒一到依然会被 PM2 一刀切强杀。

因此，在 PM2 配置中显式调大 kill_timeout 是优雅停机生效的首要前提。

3. 正确的运维部署发布命令

💡 pm2 reload 与 pm2 restart 的本质区别：

  • pm2 restart：将所有实例瞬间全部杀掉，然后再批量拉起新实例。期间服务完全不可用，必有大片停机中断！
  • pm2 reload：单实例逐个滚动更新。先启动 Instance 0，等待其发送 ready 握手信号切入流量后，再向旧的 Instance 0 发送 SIGINT 进行优雅停机；接着以此类推处理下一个实例，做到全程 0 毫秒停机中断！

五、生产环境四大典型暗坑与避坑策略

1. HTTP Keep-Alive 导致进程一直无法退出

在 HTTP/1.1 中，浏览器或反向代理（如 Nginx、CDN）会保持持久连接（Keep-Alive）。当调用 server.close() 时，Node.js 只会拒绝新建连接，但如果已建立的长连接一直空闲挂着不发请求，server.close 的回调永远不会触发！

  • 解决之道：务必在调用 server.close() 时搭配调用 Node.js 18+ 的 server.closeIdleConnections()，主动断开所有处于空闲状态的 Keep-Alive 连接。

2. 长轮询与定时器悬挂事件循环

如果项目里存在 setInterval 没有执行 clearInterval，或者未设置 timer.unref()，Node.js 的事件循环队列永远不会清空，哪怕没有请求，进程也会赖着不退直到被 PM2 强杀。

  • 解决之道：在优雅停机的清理回调中，逐一注销未完成的轮询定时器与后台定时任务。

3. Docker / K8s 容器环境下的 PID 1 信号丢失

当你在 Docker 中使用 CMD npm start 或 CMD node app.js 时，如果启动方式不当，Node.js 可能会以非 PID 1 进程运行（前面套了一层 shell），或者作为 PID 1 却无法处理信号（Linux 内核默认不为 PID 1 安装默认信号处理程序）。容器收到 docker stop 时发送的 SIGTERM 根本传递不到 Node 进程！

  • 解决之道：
    • 使用 exec 格式的 Dockerfile 指令：CMD ["node", "app.js"]；
    • 或者引入小型轻量 init 系统，如 tini：ENTRYPOINT ["/sbin/tini", "--"]。

4. 为什么不能只靠全局变量 isAppRunning = false 拦截？

有些开发者尝试在 Express 中间件里通过判断一个全局变量来返回 503 Service Unavailable。这种方式不仅增加了每个请求的处理损耗，而且对客户端依然返回了错误响应，算不上真正的平滑重载。

  • 正确做法：依靠 server.close() 让内核层停止接收 TCP 握手，同时依靠 PM2 Cluster 或上层 Nginx 的健康检查与重试机制，将新请求平稳过渡到已经就绪的新进程。
