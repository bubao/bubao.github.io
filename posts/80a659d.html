泰山派 RK3566 部署 NCNN 极速推理实践

在立创·泰山派（RK3566, 4 核 Cortex-A55, 2GB 内存）这类嵌入式 Linux 开发板上部署深度学习模型时，CPU 算力与内存带宽往往是最大掣肘。

很多开发者默认使用 ONNX Runtime CPU 模式作为落地兜底方案，但在泰山派上运行标准的 PP-OCRv4 ONNX 模型时，耗时通常长达 1.5 ~ 2 秒，且模型总体量达 90MB，内存占用极高。

而在开源项目 tspi-ocr-web 的研发过程中，我引入了腾讯开源的高性能移动端推理框架 Tencent/ncnn 与百度 PaddlePaddle/PaddleOCR 移动端轻量模型。通过开启 ARM NEON FP16 汇编加速 与 pnnx 动态尺寸图优化，将整图 OCR 识别速度直接提升至 120~180ms（性能提升近 10 倍），同时模型体量骤降至 11MB！

本文提取项目中关于 NCNN 的核心实践，系统整理“架构优势 $\to$ 模型来源与下载 $\to$ 模型转换 (pnnx) $\to$ Python 板端推理 $\to$ 性能对比与避坑”的完整落地方法论。

一、为什么选择 NCNN？

在边缘 ARM 嵌入式设备上，主流推理框架主要有 ONNX Runtime、TFLite 以及硬件专用的 NPU 工具链（如 RKNN）。但在实际工程落地中，NCNN 展现出了极其独特的不可替代性：

评估维度ONNX Runtime (CPU)瑞芯微 RKNN (NPU)腾讯 NCNN (ARM CPU)
依赖与体积依赖较重（动态库庞大）强依赖专有 NPU 内核驱动**极简纯 C++**，零第三方库依赖
模型算子兼容兼容性极强需模型量化，部分动态算子受限算子全面，图优化成熟
模型体积 (PP-OCR)约 90MB约 15MB仅 11MB（FP16 压缩）
RK3566 整图耗时~1500ms（慢）~80ms（极快）~150ms（极快，接近 NPU）
跨硬件通用性通用仅限瑞芯微指定芯片通用（任意 ARMv8/A55/A72/A76）

核心加速秘密：ARMv8.2-A NEON FP16 指令

RK3566 的 CPU 核心基于 ARM Cortex-A55 架构，支持 ARMv8.2-A 指令集中的 FP16 矢量运算。

  • 传统 ONNX Runtime 大多运行在 FP32 单精度下，不仅计算量翻倍，更严重的是在 2GB 开发板上受限于 L2/L3 缓存与 DDR4 带宽瓶颈；
  • NCNN 针对 ARM NEON 手写了深度的汇编优化内核（Kernel），计算时以 16 位半精度浮点（FP16）直接加载并执行 FMA（乘加）向量指令；
  • 双重红利：内存带宽占用直接减半，浮点吞吐率翻倍，彻底释放 4 核 A55 的硬件潜能。

三、模型转换实战：ONNX $\longrightarrow$ NCNN (基于 pnnx)

NCNN 早期使用的是 onnx2ncnn 工具，而目前官方主力推荐的是经过彻底重构的 pnnx（PyTorch/ONNX Neural Network eXchange）。pnnx 能自动完成算子融合、冗余消除以及动态尺寸定义。

在 tspi-ocr-web 项目中，转换逻辑封装在 utils/ncnn_converter.py 模块中。

3.1 安装转换工具链（建议在 PC 端执行）

虽然 pnnx 可以通过 pip 安装，但官方的 pip install pnnx 往往会强行绑定安装 500MB+ 的 PyTorch。为了保持环境纯净，可从 pnnx GitHub Releases 直接下载独立的 C++ 预编译二进制文件。

3.2 文本检测模型（DBNet）转换

文本检测模型输入通常为动态大图，若未指定输入维度，转换工具往往无法正确推导动态算子形状。需使用 inputshape 与 inputshape2 显式预设多级动态分辨率：

  • optlevel=2：启用全局算子融合与图结构裁剪；
  • fp16=1：权重大幅压缩至原大小的 50%，并在运行时开启半精度推理；
  • 产物：生成 det.ncnn.param（网络拓扑）与 det.ncnn.bin（权重参数）。

3.3 文本识别模型（CRNN / SVTR / LCNet）转换

五、RK3566 真实性能对比基准

在立创·泰山派（RK3566 4核 1.8GHz, 2GB LPDDR4, Ubuntu 26.04）上，对一张标准发票图片（包含 18 行文字）进行端到端识别测试：

推理引擎计算单元模型体量 (Det + Rec)进程常驻内存整图端到端延迟
ONNX Runtime (PP-OCRv4)CPU 4-Thread (FP32)90.4 MB~380 MB1520 ms
NCNN (PP-OCRv5)CPU 4-Thread (NEON FP16)11.2 MB~85 MB158 ms ⭐
RKNN (PP-OCRv4)NPU (0.8 TOPS INT8)14.8 MB~110 MB78 ms

从测试数据可以看出：

  1. 对比 ONNX Runtime：NCNN 速度直接提升近 10 倍，内存节省超过 **75%**，使得在 2GB 内存板卡上跑复杂视觉服务完全不会发生 OOM；
  2. 对比 RKNN NPU：NCNN 仅通过 CPU 纯算力就跑出了 150ms 的优异成绩，且完全避开了 RKNN 的 NPU 量化精度损失以及专有内核驱动门槛，非常适合快速落地交付。

六、关键避坑指南

  1. NumPy 数组连续性问题（C-Contiguous）：
    在向 ncnn.Mat 喂入切片数据（如从检测框裁剪文本小图）时，NumPy 切片通常是非连续内存。**必须调用 np.ascontiguousarray(...)**，否则可能导致底层 C++ 内存指针越界直接 Core Dump。
  2. 多线程参数设置（num_threads）：
    嵌入式多核 CPU 并非线程越多越好。在泰山派 4 核 A55 上，设置为 num_threads = 4 是吞吐与延迟的最佳平衡点；若设置过高，频繁的线程上下文切换反而会导致性能劣化。
  3. 输入输出尺寸必须符合网络步长：
    检测网络通常包含多级下采样（如 32 倍），输入的宽和高必须预处理为 32 的整数倍，否则在经过 pnnx 算子时会触发维度不匹配错误。
