如何编写一个高质量的 Agent Skill

《能做完，不等于做对：AI 时代的专业门槛》里聊过：Skill 接管了“怎么做”，却封装不了“该不该做、放在哪里”的顶层判断。这一篇往下走一步：假设你已经决定把某类工作封装成 Skill，怎么写才算写对了。

一份 Skill 的优劣不取决于写了多少，而取决于三件事：什么时候被加载、核心流程是否清晰、细节是否按需出现。这三件事分别对应文件结构、正文写法与篇幅控制，也是本文的主线。

一、先判断：这件事值不值得封装

Skill 不是提示词收藏夹。值得封装的任务，通常同时满足三个条件：

  • 重复出现：同类任务会做很多次，值得一次性写清、反复复用；
  • 质量依赖领域规则：光靠模型通用能力做不稳，需要补充特定约定、检查项或工具用法；
  • 流程可分步描述：能拆成“输入 → 步骤 → 校验”的固定套路。

一次性的临时需求、每次差异都很大的任务，写 Skill 就是浪费。

还要先确认它在架构里的位置。沿用上一篇的框架：Skill 在执行层（五层体系的第四层），管“怎么做”，管不了“放在哪、该不该做”。位置错了，写得再细也只是在错误的楼层里精装修。

二、文件结构：一个目录，一份主说明

SKILL.md 不是某一家的私有格式，它源自 Anthropic 的 Agent Skills 规范。CatPaw、Claude Code、Cursor 等主流工具都认这套「目录 + SKILL.md」，只是发现目录不同：

工具个人技能（全局可用）项目技能（随仓库共享）
CatPaw~/.catpaw/skills/<name>/.catpaw/skills/<name>/
Claude Code~/.claude/skills/<name>/.claude/skills/<name>/
Cursor~/.cursor/skills/<name>/.cursor/skills/<name>/

两点约定：

  • 各家内置目录由系统维护（如 CatPaw 的 ~/.catpaw/skills-catpaw/），不要占用；
  • 多 Agent 共用一份技能：只在一处维护原件（本地目录或 git 仓库），再软链进各家目录，避免多处拷贝导致版本漂移：

理解 Skill 的关键机制是渐进式披露：Agent 的上下文里始终只有一份“全部 Skill 清单”（name + description），命中任务时才读取 SKILL.md，用到某个细节时才加载附属文件。

flowchart LR
    A["用户任务"] --> B["Agent 扫描 Skill 清单
只看 name + description"]
    B --> C{"命中触发场景？"}
    C -- 否 --> D["用通用能力直接处理"]
    C -- 是 --> E["加载 SKILL.md
核心流程与约束"]
    E --> F["按需读取附属文件
reference.md / examples.md / scripts/"]
    F --> G["按流程执行并校验输出"]

这个机制直接决定写法：SKILL.md 必须自包含核心流程，但绝不能塞满细节。塞多了既占上下文，也拖慢每一次加载。

三、description：决定触发成败的字段

Agent 完全依赖 description 判断某个任务该不该用这个 Skill。它会被注入系统提示词，因此有三个硬性要求：

  1. 第三人称陈述，而不是“我可以帮你……”这类对话口吻；
  2. 写清 WHAT + WHEN：这个 Skill 做什么 + 什么时候应该用它；
  3. 包含触发词：覆盖用户可能用来描述这类任务的说法，包括同义词与口语表达。
反面正面
帮助处理 PDF提取 PDF 文本与表格、合并文档。当用户提到 PDF、表单、文档提取时使用
辅助开发按博客规范创建 Hexo 文章：生成 front matter、摘要断点与编号章节。当用户要求写博客、新建文章时使用

一个可套用的公式是：「做什么（动词 + 对象）+ 产出什么 + 什么时候用（触发场景/关键词）」。例如「创建 Hexo 文章，生成 front matter、摘要断点与编号章节；当用户要求写博客、新建文章时使用」。

name 的要求：小写字母、数字、连字符，不超过 64 字符，拒绝 helper、utils 这类看不出用途的泛名。必填字段之外的可选元数据各家支持不同（如 Claude Code 的 allowed-tools、CatPaw 的 metadata 块），按所用工具按需补充。

四、正文：只写 Agent 不知道的

上下文是共享资源，每段话都要过一遍“这句话值不值这些 token”。默认假设 Agent 已经很聪明——通用常识不用写，值得写的只有五类信息：领域规则、项目约定、固定步骤、验收标准、易错点。

常用组织模式：

  • 工作流模式：编号步骤 + checklist，让 Agent 逐项推进并自查，适合步骤多、容易漏项的任务；
  • 条件分支：先判断任务类型再分叉，比如“新建内容走 A 流程，修改内容走 B 流程”，避免一条道走到黑；
  • 模板模式：给出输出格式骨架，对格式敏感的任务（报告、提交信息）特别有效；
  • 示例模式：输入 → 输出的完整例子，比抽象规则更不容易被曲解；
  • 反馈循环：执行 → 跑校验 → 失败修复 → 通过才继续，守住质量下限。

写法上还有一个“自由度”取舍，取决于任务有多脆弱：

自由度形式适用场景
高文字指南方案评审、代码审查：解法多样、依赖上下文
中模板 / 骨架报告生成、格式化输出：有偏好但允许变化
低具体脚本数据迁移、发版：步骤脆弱、一致性压倒一切

任务越脆弱、越要求每次结果一致，就越应该下沉到脚本，而不是停留在文字建议。

五、渐进披露：控制篇幅，善用附属文件

  • SKILL.md 控制在 500 行以内（越短越好），保证“扫一眼就知道怎么干”；
  • 细节搬进 reference.md / examples.md，从 SKILL.md 一层链接过去——不要嵌套引用，Agent 可能只读主文件；
  • 需要精确复现的操作，直接提供 scripts/ 里的脚本让 Agent 执行：比现场生成代码更可靠、更省 token，且每次行为一致。在 SKILL.md 里写明脚本是“执行”还是“参考”。

六、反模式与验收清单

常见的坑：

  • 选项瘫痪：列了 A/B/C 三种库都行——不如给一个默认选项，补一句“特殊情况才用 B”；
  • 时效性信息：不要写“某年某月之前用旧接口”，过时的分支判断会把 Agent 带偏；
  • 术语漂移：同一概念统一叫法，别一会儿“接口”一会儿“路由”；
  • 名字太泛：processing-pdfs 远好于 utils。

发布前过一遍清单：

  • description 第三人称、有 WHAT/WHEN、包含触发词；
  • SKILL.md 不超过 500 行，引用文件只有一层深；
  • 有默认选项、术语一致、无时效性内容；
  • 实测：在真实对话里看它能否在正确时机被触发，附属文件是否被按需读取；多 Agent 共用的，逐个端验证一遍。

七、一个完整的最小示例

一份够用的 Skill，通常 30–80 行就能成立。真正难的从来不是把文件写长，而是把判断写清楚——哪些步骤不能跳、哪些细节什么时候才需要、什么样的输出算合格。这恰好又回到最初那件事：Skill 越标准，人越要清楚它标准的边界在哪里。
