Nginx 工程实践 -- 6. 限流与安全响应头

防盗链防的是"来源"，鉴权防的是"身份"，这一篇补上"强度"维度：限制请求速率、并发连接和下载速度，再统一加上安全响应头。这些都是网关层成本极低、收益极高的防护。

二、请求速率：limit_req

limit_req_zone 定义在 http 块，limit_req 使用在 server/location：

Nginx 用**漏桶（leaky bucket）**算法：请求按配置的速率被放行，超出的部分先进入 burst 队列，队列也满了才直接拒绝。

参数说明
rate放行速率，单位 r/s；小于 1 用 r/m（如 30r/m 表示每两秒一个）
burst允许的突发量，默认 0；超过 burst 的请求被拒绝
nodelay队列里的请求不延迟、立即放行（但仍计入速率）；适合接口类场景
delay=N只延迟前 N 个，其余直接放行（较新版本支持）
limit_req_status拒绝时返回的状态码，默认 503

limit_req_log_level 控制触发限流时的日志级别，配合 $limit_req_status（PASSED / DELAYED / REJECTED）可以观察限流行为。

三、并发连接：limit_conn

限制的是"同一 key 同时处于处理中的连接数"。注意：只有请求头已读完、正在处理的连接才计数。在 HTTP/2 和 HTTP/3 中，每个并发请求算作一个独立连接，这与 HTTP/1.1 的语义不同。

四、下载限速：limit_rate

用于限制单个连接的下载速度，常和断点续传（Range）一起用，避免大文件把带宽吃满。limit_rate_after 可以设置"先免费一段再限速"。

五、key 的选择

  • $binary_remote_addr：IPv4 固定 4 字节、IPv6 固定 16 字节，比 $remote_addr 更省内存，是限流的默认推荐 key；
  • $server_name：按站点维度限流；
  • 组合 key：$binary_remote_addr$request_uri、$binary_remote_addr$cookie_session，可做更细的策略。

注意：按 IP 限流对 NAT / 移动网络用户会"误伤"（多人共享出口 IP），对代理后的场景则可能失效——这正是第 4 篇要先还原真实 IP 的原因。

要点：

  • server_tokens off 隐藏版本号，减少无谓的信息暴露；
  • add_header 默认只对 200 201 204 206 301 302 303 304 307 308 生效，安全头要加 always，否则 4xx/5xx 响应上不会带；
  • HSTS 只在 HTTPS 下才有意义（RFC 6797），首次访问前不设防，需要配合preload 列表才更完整；
  • X-Frame-Options 已被 CSP 的 frame-ancestors 取代，新站点建议直接写 CSP；
  • CSP 是"白名单"机制，上线前建议先 Content-Security-Policy-Report-Only 观察。

七、add_header 的继承陷阱

Nginx 的规则是：当前层级只要定义了任意一条 add_header，就不再继承上一层的所有 add_header。于是常见现象是——server 块配好了安全头，某个 location 里为了加一个头又写了一条 add_header，结果安全头全丢了。

两种解决方式：

  • 抽 snippet：把安全头集中在一个文件里，各处 include（推荐）；
  • 新版本指令：add_header_inherit merge;（较新版本支持）可以改变继承规则。

同样的坑也出现在 expires 与 add_header Cache-Control：expires 会自己写 Cache-Control，再 add_header Cache-Control 会得到两个头（第 1 篇已提到）。

小结

限流用漏桶（rate + burst），并发用 limit_conn，下载用 limit_rate；key 优先 $binary_remote_addr。安全头统一抽成 snippet 并用 always，注意 add_header "定义即不继承"的坑。所有策略生效的前提是——第 4 篇里先把真实客户端 IP 还原对。
