Node.js 实现断点下载器

本文从 HTTP/1.1 Range 分片传输协议（RFC 7233）出发，深入剖析断点续传的协商与一致性校验机制，并基于现代 Node.js 原生模块实现一套支持状态码自适应降级、原子持久化与优雅中断的工业级下载器。

在编写命令行下载工具（如我早期开发的 eva）或处理大文件拉取业务时，网络波动导致的连接中断、弱网环境超时以及意外关闭终端是无法避免的现实问题。

如果一个 2GB 的资源在下载到 99% 时断网，缺乏断点续传机制的下载器就必须“从零重开”，这不仅极度损耗用户体验，更白白消耗宝贵的服务器带宽。

一、HTTP 断点续传协议核心机制 (RFC 7233)

所谓“断点续传”，本质上是客户端与服务端基于 HTTP 协议头完成的一场分片范围协商。

1. 协商三部曲：探测、范围请求与响应

  1. 预检与能力探测（Accept-Ranges）：通过发送 HEAD 请求获取目标资源的基础元信息。若响应头包含 Accept-Ranges: bytes，则证明服务器支持基于字节偏移的局部读取。
  2. 请求指定字节区间（Range）：客户端根据本地已下载的文件字节数（如 1024 字节），在后续 GET 请求中附带请求头：表示“从第 1024 字节开始，请求直到文件末尾的所有数据”。
  3. 分片响应状态码（206 Partial Content）：
    • 支持断点续传：服务端返回 206 Partial Content，并在响应头中通过 Content-Range 标明当前切片的起止范围与总大小（例如 Content-Range: bytes 1024-5242879/5242880）；
    • 不支持断点续传：服务端会直接忽略 Range 头，返回标准的 200 OK，并从第 0 字节开始推送完整内容。客户端必须对此做好平滑降级（改为全量覆写）。

2. 避免数据污染的关键：资源一致性校验 (If-Range / ETag)

在断点续传的间隔期内，服务端的文件内容可能已经被重新发布或修改。如果客户端继续拿着旧文件的字节偏移去追加新文件的尾部，最终拼合出的必然是一个彻底损坏的乱码文件。

为了避免这种静默的数据污染，必须引入一致性校验：

  • ETag / Last-Modified：首次请求时保存资源的实体标签（ETag）或最后修改时间；
  • If-Range：续传时将 ETag 作为 If-Range 头的值带上。若资源未变，服务器返回 206 继续下载；若资源已变动，服务器会自动判定失效并直接返回 200 全量数据，此时客户端应重新创建文件并从头写入。

二、Node.js 核心机制与工程要点

在 Node.js 中构建断点下载器，核心是围绕 fs 模块与 stream 模块做流转调度：

  1. 已存在字节探测：使用 fs.promises.stat(partFilePath) 获取本地已写入的字节尺寸 stats.size，以此确定 Range 请求的起始偏移量。
  2. 文件写入模式（flags: 'a' vs flags: 'w'）：
    • 收到 206 Partial Content 时：使用 fs.createWriteStream(filePath, { flags: 'a' }) 以追加模式将流接入文件尾部；
    • 收到 200 OK 时：必须切换为 { flags: 'w' }（或清空旧临时文件），防止将全量数据拼接在旧残片后面造成体积翻倍。
  3. 临时文件（.part）原子重命名机制：为了防止网络中断留下半成品文件被其他程序误当成完整文件处理，在下载期间所有数据必须写入临时文件（如 target.zip.part）。只有当流触发 finish / close 且完成大小校验后，再调用 fs.promises.rename 原子重命名为目标文件名。
  4. 流式背压与安全流管道（stream.pipeline）：早期的 .pipe() 无法自动处理管道中的双向错误捕获与流销毁，容易引发内存泄漏或文件句柄挂起。现代 Node.js 推荐使用 stream.promises.pipeline 或标准 Web Streams API。
  5. 实时进度、瞬时速度与 ETA 计算：
    • 瞬时下载速率：固定采样周期（如 1000ms），统计该周期内接收的字节差值： $$\text{Speed} = \frac{\Delta \text{Bytes}}{\Delta t}$$
    • 剩余预估时间（ETA）： $$\text{ETA} = \frac{\text{TotalBytes} - \text{CompletedBytes}}{\text{Speed}}$$

历史设计的不足与现代演进反思

  1. 上游生态变迁： request 库早在 2020 年就已正式宣布弃用（Deprecated）。现代工程应当拥抱 Node.js 原生的 node:http / node:https，或通过 fetch + Web Streams 保持零外部运行时依赖。
  2. 防范数据损坏的健壮性：早期代码直接写入最终目标路径，如果下载中途被 Ctrl + C 强杀，本地留下的半截文件可能直接误导外部解析程序；现代设计必须引入 .part 临时后缀 + 原子 rename 机制。
  3. 缺少预检与状态码分支：早期假设服务端必然支持 Range，如果服务端实际上返回了 200 OK，追加模式（flags: "a"）就会导致新旧两份文件堆叠在一起，文件直接报废。新版本必须严格区分 206 与 200 状态码。

五、工业级落地的边界条件与避坑要点

  1. HTTP 416 (Range Not Satisfiable) 陷阱：当本地 .part 临时文件的体积因为某种异常（例如之前的下载被服务器强制重定向或写入了 HTML 错误页）大于等于服务端的真实文件大小时，服务端会返回 HTTP 416。遇到 416 时必须主动清空本地损坏的分片，重新发起全量下载。
  2. CDN 与反向代理的压缩干扰（Gzip / Brotli）：如果服务端对大文件开启了动态压缩，响应头可能缺失 Content-Length，或者返回的是压缩流的长度，导致字节偏移与实际解压后的文件脱节。在请求头中显式声明 Accept-Encoding: identity 可指示服务端不要压缩二进制文件。
  3. 多连接并行切片（Multi-threading Chunked Download）：对于超大文件（如数十 GB），断点续传常与多线程并发结合：预先获取总大小，按照 10MB 分片向不同线程分配 Range: bytes=0-10485759、Range: bytes=10485760-20971519，各个分片独立下载为 .part.0、.part.1，最后通过文件流按序合并。

结语

一个健壮的断点续传器不仅是几行 HTTP 头的堆叠，更是一套包含了协议协商预检、状态码自适应降级、数据流背压控制、原子文件状态机以及优雅中断的系统化网络工程实践。
