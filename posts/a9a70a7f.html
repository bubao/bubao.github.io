解决 Git status 中文文件名乱码

在使用 Git 管理包含中文文件名或中文 Commit 信息的项目时，几乎所有开发者都曾被以下诡异的“乱码”现象折磨过：

  1. git status 抓狂现场：工作区新添加了一个中文文件（如 架构设计图.png），终端不仅不显示中文，反而打印出一长串带双引号的反斜杠八进制数字：
  2. git log 灾难现场：团队成员辛辛苦苦写的中文提交信息，查看历史时全变成了类似 <E4><BD><A0><E5><A5><BD> 的乱码字符或者完全无法辨识的方块。
  3. git diff 痛苦现场：对比代码差异时，中文字符被截断或者展示为问号，极度干扰 Code Review。

很多人以为这只是终端字体缺失，其实背后交织着 Git 默认路径转义策略（core.quotepath）、提交编码声明、分页器（Pager / less）字符集 以及 Windows/macOS 操作系统底层的编码差异。

本文将手把手拆解这些乱码的底层根因，并给出适用于 Windows、macOS 与 Linux 的终极一键配置。

1. 为什么文件名会变成 \346\236\266？—— core.quotepath 机制

在 Git 的设计之初，主要面向欧美开发者。为了防止在不同操作系统中由于换行符、不可见控制字符或不同区域编码引发文件名歧义，Git 内置了一个安全策略：

core.quotepath 默认值为 true。只要文件名中包含任何 ASCII 码大于 0x80（即十进制 128）的字符，Git 就会自动用双引号将其包裹，并将其 UTF-8 字节逐个转换为 \八进制 进行转义输出！

汉字“架”的 UTF-8 编码为三个字节：十六进制 E6 9E B6，转换为八进制恰好就是：

  • E6 $\to$ \346
  • 9E $\to$ \236
  • B6 $\to$ \266

所以你看到的不是乱码，而是 Git 忠实呈现的 UTF-8 字节八进制转义串！通过设置 git config --global core.quotepath false，我们告诉 Git：“我的终端现代且完全支持 UTF-8，请直接原样把原始字节流吐给终端显示，不要自作聪明进行转义！”

2. 为什么 git log 会显示为 <E4><BD><A0>？—— Pager 与输出编码

当提交信息中包含中文时，Git 需要明确两件事：

  • 存入版本库时用什么编码（i18n.commit.encoding）：如果不配置，在老系统上可能会使用本地编码（如 Windows 下的 GBK），导致提交被推到 GitHub 后在网页端全变成乱码；
  • 展示给屏幕时用什么编码（i18n.logoutputencoding）：如果终端是 UTF-8 环境，而该项未对齐，就会产生解码异常。

2. macOS 专属暗坑：NFD 与 NFC 规范化幽灵冲突

macOS 开发者在跨平台协作时，经常会遇到一个极其奇葩的灵异事件：

“明明我什么都没改，但在 Linux 服务器或 Windows 同事那边 pull 下来，Git 却提示某些中文命名的文件被重命名（Rename）或发生了莫名其妙的冲突！”

根因剖析：Unicode 规范化形式差异

  • macOS 历史文件系统（HFS+ / APFS）：底层强制使用 NFD（Normalization Form D，完全分解形式）。例如汉字“好”，它会被分解为独立的辅音/元音或基字符与变音符号组合；
  • Linux / Windows 系统：普遍采用 NFC（Normalization Form C，预组合形式），即一个汉字对应一个完整的复合码点。

表面上看长得一模一样，但底层的二进制字节完全不同！这就导致 Git 在比对文件索引时误以为是两个完全不同的文件名。
