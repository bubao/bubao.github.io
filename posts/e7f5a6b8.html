Nginx 工程实践 -- 8. 压缩与 HTTP/2、HTTP/3

HTML、CSS、JS、JSON、SVG 这些文本资源通常占页面流量的绝大部分，压缩它们是最直接的提速手段。而 HTTP/2、HTTP/3 则从协议层解决"队头阻塞、连接数爆炸、握手往返多"的问题。两者目标不同：压缩减少传输字节，新协议改善连接与并发模型。

一、gzip 模块

关键指令：

指令默认说明
gzipoff开关，可出现在 http/server/location
gzip_min_length20响应小于该长度不压缩（按 Content-Length 判断）
gzip_comp_level1压缩级别 1–9，越高越省流量但越吃 CPU
gzip_typestext/html额外压缩的 MIME；text/html 永远压缩
gzip_varyoff是否追加 Vary: Accept-Encoding
gzip_proxiedoff对代理请求是否压缩（any = 总是）
gzip_disable—按 User-Agent 正则禁用，内置 msie6 掩码
gzip_http_version1.1触发压缩所需的最低 HTTP 版本

经验值：

  • gzip_min_length 1024 左右即可，太小的响应压缩收益不抵开销；
  • gzip_comp_level 用 4–6 是性价比区间，再往上 CPU 成本上升明显；
  • 只压文本类。图片、视频、PDF、字体、已压缩包本身已是压缩格式，再压一遍几乎无收益还浪费 CPU；
  • gzip_vary on 建议打开，否则中间缓存可能把压缩版发给不支持 gzip 的客户端；
  • 想观测压缩效果，在 log_format 里加 $gzip_ratio（原始/压缩比）。

二、预压缩：gzip_static

实时压缩每个响应都要消耗 CPU。如果构建阶段已经生成了 .gz，可以让 Nginx 直接发：

  • 构建产物里要存在 app.js.gz 这类文件（Webpack/Vite 可通过插件输出）；
  • gzip_static on 时不消耗压缩 CPU，TTFB 也更好；
  • gunzip on 兜底老客户端，但会临时解压占内存，视流量决定是否开。

三、brotli（可选，第三方模块）

gzip 之外，Brotli（br）对文本资源通常压缩率更高，是 HTTP 时代的事实标准之一。Nginx 官方未内置，需用第三方模块 google/ngx_brotli 自行编译。配置形态与 gzip 类似（brotli on; brotli_types ...; brotli_comp_level ...;），并注意 Vary: Accept-Encoding 的语义一致。

四、压缩与安全、缓存的相互作用

  • TLS + 压缩 = BREACH 风险：ngx_http_gzip_module 官方文档明确提示，压缩后的响应在 TLS 下可能受到 BREACH 攻击（利用压缩比推断敏感内容）。涉及机密数据的接口可单独关 gzip；
  • 不要重复压缩：上游若已返回 Content-Encoding: gzip，Nginx 再开 gzip 会造成双重压缩，proxy_set_header Accept-Encoding ""; 或 proxy_hide_header Content-Encoding 之类要按场景处理；
  • 压缩与缓存顺序：Nginx 的 proxy_cache 存的是压缩后的响应体，缓存键里通常不含 Accept-Encoding，所以靠 Vary 让中间层区分，Nginx 自身不会为不同编码分别缓存（除非显式把 $http_accept_encoding 加进 proxy_cache_key，一般不建议）。

五、HTTP/2

要点：

  • 写法变了：旧版是 listen 443 ssl http2;，1.25.1 起新增 http2 on; 指令，推荐使用 http2 on;；
  • HTTP/2 over TLS 依赖 ALPN 扩展，需要 OpenSSL 1.0.2+；
  • 模块默认不编译，需 --with-http_v2_module；
  • 价值：多路复用（一个连接多个并发流）、HPACK 头部压缩、二进制分帧，缓解 HTTP/1.1 的队头阻塞；
  • 相关指令：http2_max_concurrent_streams（默认 128）、http2_chunk_size（默认 8k，响应分块大小，太小开销大、太大影响优先级）；
  • 服务器推送相关指令（http2_push、http2_push_preload）已废弃，建议改用 early_hints（103 Early Hints）或 <link rel="preload">；
  • 排查协商结果：日志里加 $http2，值为 h2 即 HTTP/2。

六、HTTP/3（实验性）

HTTP/3 跑在 QUIC（UDP）上，解决了 TCP 层的队头阻塞，并让连接迁移成为可能。Nginx 从 1.25.0 起通过 ngx_http_v3_module 提供实验性支持：

要点与限制：

  • 模块默认不编译，需 --with-http_v3_module，并要求 OpenSSL 1.1.1+（0-RTT 需 OpenSSL 3.5.1+ 或 BoringSSL/LibreSSL/QuicTLS）；
  • 官方明确标注实验性（“caveat emptor”），生产启用前要自行评估；
  • 变量 $http3 为 h3 表示当前走 HTTP/3；
  • quic_retry on 开启 QUIC 地址验证，缓解放大攻击；
  • quic_bpf on（仅 Linux 5.7+）可在 reload / 热升级时保留已建立的 QUIC 连接，支持连接迁移；
  • 浏览器通过 Alt-Svc 发现 HTTP/3，ma 是缓存秒数。

七、常见问题

现象原因 / 处理
图片/视频体积没变gzip_types 里写了图片 MIME 或用了 *；移除即可
浏览器拿到未压缩内容客户端不支持、响应小于 gzip_min_length、或上游已带 Content-Encoding
响应出现两个 Content-Encoding上游已压缩，Nginx 又压了一次
中间缓存命中异常缺 Vary: Accept-Encoding；开 gzip_vary on
HTTP/2 不生效模块未编译；仍写 listen ... http2 的旧机器上语法被改
HTTP/3 连不上防火墙没放行 UDP 端口；模块未编译；客户端不支持
压缩 CPU 偏高gzip_comp_level 调低、或改用 gzip_static 预压缩

小结

  • gzip 只压文本类 MIME，gzip_min_length/gzip_comp_level 取性价比区间，gzip_vary on 别忘；
  • 有构建流程就用 gzip_static 预压缩，省 CPU；
  • TLS 下压缩有 BREACH 风险，敏感接口单独关；上游已压缩就别再压；
  • HTTP/2 用 http2 on;，确认模块已编译、日志 $http2 为 h2；
  • HTTP/3 仍是实验特性，启用前评估 quic_retry、Alt-Svc 与 UDP 防火墙。
