一直被误解的 GET 请求

从刚接触 Web 开发开始，各种技术面试和博客里就充斥着一道经典八股文：

“HTTP 的 GET 请求和 POST 请求有什么区别？”

大部分教材或题库给出的标准答案无非是这几句：

  • ❌ “GET 参数必须放在 URL 上，POST 才能带 Body（请求体）；”
  • ❌ “GET 请求有长度限制，POST 请求长度没有限制；”
  • ❌ “POST 比 GET 更加安全。”

然而，只要翻一翻底层的 HTTP 协议标准与底层报文格式，就会发现这些说法充满了对规范的误读与混淆。

本文通过 Node.js 原生代码亲自动手验证，并结合最新的 RFC 官方协议规范，彻底还原 GET 请求在 HTTP 报文中的真实面貌。

一、动手实测：GET 请求到底能不能携带 Body？

在 HTTP/1.1 协议中，请求报文由四部分组成：请求行、请求头、空行、请求体（Entity-Body）。

在协议语法层面，请求体就是一个跟在两个连续换行符 \r\n\r\n 后面的数据流，它并不是 POST 的专属特权。

二、RFC 官方协议到底是怎么规定的？

为什么大家都习惯性认为 GET 不能带 Body？我们来查阅 IETF 官方起草的权威 RFC 文档：

1. RFC 2616 (早期的 HTTP/1.1 标准)

在 RFC 2616 第 4.3 节中，关于消息主体的定义仅说明了某些特定的方法（如 HEAD）不能有主体，而从未禁止 GET 请求发送 Entity-Body。

2. RFC 7231 / RFC 9110 (现代 HTTP 核心语义规范)

在更新后的 RFC 7231 第 4.3.1 节（并在 2022 年发布的 RFC 9110 中进一步确认），官方做出了非常严谨的界定：

“A payload within a GET request message has no defined semantics; sending a payload body on a GET request might cause some existing implementations to reject the request.”

(GET 请求中的有效载荷并没有被定义任何标准语义；在 GET 请求上发送请求体可能会导致某些现有的软件实现拒绝该请求。)

这意味着：

  • 语法层面（Syntax）：完全合法，符合 HTTP 报文分段规范；
  • 语义层面（Semantics）：RFC 没有赋予它任何标准行为。RFC 并没有说“这是非法的”，而是说“协议没有定义它该怎么用，因此不同的中间件实现可能会做出不同反应”。

3. 工业界的现实案例：Elasticsearch

三、既然协议允许，为什么日常开发中“GET 带 Body 会丢”？

既然底层协议完全可行，为什么在日常 Web 开发中，大家依然坚决不建议在 GET 里传 Body？

这并非 HTTP 协议的限制，而是整个上下游软件生态的“潜规则”与实现约束：

  1. 浏览器规范的强制拦截：在浏览器控制台执行原生 Fetch API：浏览器会毫不留情地抛出致命错误：TypeError: Failed to execute 'fetch' on 'Window': Request with GET/HEAD method cannot have body. （浏览器为了保障跨端一致性，在前端 API 规范层直接将其封杀了）。
  2. 中间代理与网关的丢弃：很多 CDN、反向代理（如部分 Nginx 模块、负载均衡器）或防火墙在解析到 GET 时，出于安全或协议优化的考量，会自动剥离甚至直接丢弃请求体，导致请求到达后端服务器时 Body 变为空。
  3. HTTP 缓存体系的崩溃： GET 请求是原生支持强缓存的。代理服务器与浏览器缓存是以 URL 作为缓存 Key 的。如果 GET 请求的响应结果取决于 Body，那么缓存网关将完全无法判断多次请求是否返回相同内容，导致缓存机制彻底失效。

四、破解迷思 2：GET 请求的 URL 真的有长度限制吗？

另一个流传甚广的误解是：“GET 传参有 2KB 限制，POST 没有限制”。

真相是：HTTP 协议规范中从未对 URL 长度做过任何字节限制！

如果 URL 太长，协议只定义了服务器可以返回一个状态码：414 URI Too Long。而现实生活中的长度瓶颈，完全来自具体的客户端与服务器配置：

软件 / 环节限制原因与典型阈值
微软旧版 IE 浏览器历史上硬编码限制为 2083 个字符（这是 2KB 谣言的始作俑者）
现代浏览器 (Chrome / Firefox)Chrome 限制约为 32KB，Firefox 限制约为 64KB
Nginx Web 服务器由 large_client_header_buffers 控制，默认单行 Header 通常限制为 4KB ~ 8KB，超限即报 414
Apache Web 服务器默认由 LimitRequestLine 控制，通常为 8KB

之所以建议大型数据使用 POST，是因为 POST 将数据放在请求体中，通过流式传输不仅容量几乎不受限制，而且不会被记入 Web 访问日志或浏览器历史记录，避免了敏感信息泄露。

五、GET 与 POST 的真正本质区别到底是什么？

丢掉表面的参数位置与长度限制，RESTful 架构与 HTTP 规范中两者最根本的区别在于三大约束特征：

核心特性GET 方法POST 方法深入解读与工程影响
安全性 (Safe)✅ 是（只读操作）❌ 否（写操作）用户查询页面，不应导致服务器内部数据状态被修改（严禁通过 GET 执行扣款、删除等破坏性动作）
幂等性 (Idempotent)✅ 是（请求 1 次与 N 次效果相同）❌ 否（每次执行都会产生副作用）网络抖动超时时，客户端可安全重试 GET；而重试 POST 会导致重复下单或扣款（浏览器会提示“确认重新提交表单”）
可缓存性 (Cacheable)✅ 是（默认可被强缓存）❌ 否（默认不可缓存）浏览器、网关与 CDN 默认可基于 URL 强缓存 GET 的响应结果，POST 由于携带个性化业务数据默认不被缓存
语义定位获取指定资源的当前表示形式向目标资源提交待处理的实体数据遵从 HTTP 语义中“获取”与“提交/变更”的职责分离

总结

  • GET 可以传 Body 吗？ 协议从未禁止，语法完全合法；但在 Web 浏览器与公共 CDN 生态中，由于实现差异可能会被丢弃。
  • GET 有长度限制吗？ HTTP 协议没有限制，限制是由于各个浏览器与 Web 服务器的默认缓冲区大小造成的。
  • 真正区分 GET 与 POST 的，从不是“谁能带 Body”或者“谁的 URL 更长”，而是它们的语义设计、安全属性与幂等性承诺。
